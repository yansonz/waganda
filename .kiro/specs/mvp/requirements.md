# Requirements Document

> **서비스명: 와간다 (Waganda)** — "와인이 간다"

## Introduction

### 배경

`docs/proposal.md`에서 아이데이션한 **와간다(Waganda)** 는 부부(Yan & Robert)가 와인을 마신 순간의
첫 반응을 음성으로 녹음하고, AI가 이를 재미있는 리뷰·평점·테이스팅 노트로 변환해 기록하는
와인 시음 저널이다.

원본 제안서는 Vercel + Supabase + OpenAI 직접 호출을 전제로 했으나, 본 스펙은 두 가지 방향으로
재정의한다.

1. **AWS 단일 클라우드 운영** — 호스팅·DB·스토리지·큐·모델 추론을 모두 AWS로 통일한다.
2. **Agentic 애플리케이션** — 고정 파이프라인이 아니라, 도구(tool)를 스스로 선택·조합하고
   기억(memory)을 활용하는 **에이전트**가 분석·추천·패턴 발견을 수행한다. AWS 상에서 에이전트를
   배포·운영·관측하는 경험 자체가 이 프로젝트의 학습 목표 중 하나다.

또한 이 저널은 **로그인 없이 누구나 열람할 수 있는 공개 서비스**로 운영한다. 부부의 기록을
공개 아카이브처럼 보여주고, 기록 생성·수정은 지정된 Google 계정으로 로그인한 편집자에게만
허용한다.

### 목적

- 부부 2인이 실제로 즐겁게 쓰는 와인 저널을 만든다. (재미 > 정확도)
- 짧고 비전문적인 반응("와", "음...", 3초 침묵)에서 최대한 의미를 뽑아내는 AI 경험을 구현한다.
- 의도적으로 찾지 않아도 **누적 데이터에서 뜻밖의 패턴이 저절로 드러나는** 경험을 만든다.
- AWS 상에서 프로덕션 agentic 앱을 설계·배포·관측·비용통제하는 경험을 축적한다.

### 범위 (In Scope)

| 영역 | 내용 |
| --- | --- |
| 공개 | 로그인 없는 전체 열람, 공유용 메타데이터, Google OAuth 편집자 인증 |
| 기록 | 음성 녹음/업로드, 라벨 촬영, 와인 메타데이터 입력 |
| 에이전트 | 라벨 인식, 시음 분석(소믈리에), 취향 프로파일, 패턴 발견 |
| 재미 요소 | 재미있는 반응 하이라이트, 두 화자 반응 일치도, 뜻밖의 패턴 발견 카드 |
| 탐색 | 와인별/와이너리별/지역별/타임라인/평점순 뷰, 상세 페이지 |
| 운영 | AWS IaC 배포, CI/CD, 에이전트 관측성, 남용/비용 가드레일 |

### 범위 외 (Out of Scope)

- 셀프 회원가입, 자체 비밀번호 인증, 3인 이상 편집자 확장 (편집 권한은 허용 목록에 등록된 Google 계정 OAuth로만 부여)
- 3인 이상 다중 테넌시, 외부 사용자 초대, 댓글·좋아요 등 소셜 인터랙션
- 시음자 수동 입력 및 개인별 취향 프로파일 (화자는 음성에서 자동 추정하며, 취향 프로파일은 부부 공통 하나만 유지)
- AI 리뷰어 페르소나(말투 프리셋) 전환 기능
- 부부 대결·평점 베팅, 도장깨기·뱃지·스트릭 등 게임화 요소
- 사용자가 직접 가설을 등록하고 적중률을 관리하는 이론 검증 기능
- 결제/구독, 와인 커머스 연동, 실시간 가격 크롤링
- 모바일 네이티브 앱 (모바일 웹 반응형으로 대응)
- 전문 소믈리에 수준의 정량적 관능 평가 정확도 보장

### 단계 구분

각 Requirement에 `**Phase:**` 를 표기한다. **Phase 1 = MVP**(먼저 구현), **Phase 2** = MVP 안정화 후.

- **Phase 1**: Requirement 1 ~ 11
- **Phase 2**: Requirement 12 ~ 14

## Glossary

| 용어 | 정의 |
| --- | --- |
| 시음 세션(Tasting Session) | 한 와인을 한 시점에 부부가 함께 마시며 기록한 단위. 녹음 1개 이상을 포함한다. 시음자는 항상 부부 2인이므로 별도로 기록하지 않는다. |
| 화자(Speaker) | 트랜스크립션의 화자 분리로 자동 구분된 발화 주체. 화자별 평균 피치로 성별을 추정해 남성 화자를 `yan`, 여성 화자를 `robert`로 간주한다. |
| 편집자(Editor) | 허용 목록에 등록된 Google 계정으로 OAuth 로그인한 사용자. 개별 식별 없이 모두 동일한 쓰기 권한을 갖는다. |
| 허용 목록(Allowlist) | 편집자로 인정할 Google 계정 이메일의 서버 측 목록. Yan과 Robert의 계정 2개로 구성한다. |
| 반응 하이라이트(Highlight) | 녹음 중 의미 있는 순간을 AI가 뽑아낸 짧은 인용/서술. 말풍선 UI로 표시. |
| 음향 특징(Acoustic Feature) | 오디오에서 추출한 수치 신호(RMS 에너지, 피치, 침묵 구간, 발화 속도, 웃음 후보 구간). 감정 추론의 입력. |
| 에이전트(Agent) | LLM이 도구를 스스로 선택·호출하며 다단계로 목표를 달성하는 실행 단위. 고정 순서 파이프라인과 구분된다. |
| 도구(Tool) | 에이전트가 호출 가능한 함수(DB 조회, 텍스트 검색, 통계 계산, 웹 검색 등). |
| 취향 프로파일(Taste Profile) | 누적 시음 기록에서 도출한 부부 공통 선호 속성 요약 + 5축 점수 벡터. 개인별로 분리하지 않는다. |
| 발견 카드(Discovery Card) | 누적 데이터 탐색 중 에이전트가 우연히 찾아낸 패턴을 서술·근거·표본수와 함께 제시하는 카드. |
| 비전통 축(Non-conventional Axis) | 품종·지역·가격 같은 정통 축이 아닌 탐색 축. 라벨 시각 태그, 병/마감 형태, 시음 시각·요일, 음향 특징 등. |
| 반응 일치도(Chemistry Score) | 한 시음 세션에서 두 화자의 감정 강도·평가 방향이 얼마나 일치했는지를 0~100으로 환산한 값. |
| 가드레일(Guardrail) | 에이전트의 토큰/비용/실행시간/도구호출 횟수 상한과 안전 정책. |
| 트레이스(Trace) | 에이전트의 사고 단계·도구 호출·토큰 사용량을 시간순으로 기록한 관측 데이터. |

## Requirements

### Requirement 1: 공개 열람과 Google OAuth 기반 쓰기 권한

**User Story:** As a 부부 사용자, I want 우리 기록은 누구나 로그인 없이 볼 수 있고, 뭔가 고치려고 할 때만 우리 구글 계정으로 로그인하기를, so that 링크만 보내도 구경할 수 있으면서 평소에는 로그인을 신경 쓰지 않는다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 로그인이나 계정 생성 없이 모든 시음 기록, 와인 카탈로그, 통계, 탐색 화면을 열람할 수 있게 한다.
- THE System SHALL 자체 회원가입과 자체 비밀번호 인증을 제공하지 않는다.
- THE System SHALL 공개 페이지에 공유용 메타데이터(제목, 설명, 대표 이미지)를 제공한다.
- THE System SHALL 편집자 로그인을 Google OAuth 2.0 Authorization Code 흐름으로만 처리한다.
- THE System SHALL 서버 측 **허용 목록**에 등록된 Google 계정 이메일만 편집자로 인정한다.
- THE System SHALL Google 프로필의 이메일 인증 여부(`verified_email`)를 확인하고, 미인증 이메일은 거부한다.
- IF 허용 목록에 없는 Google 계정이 OAuth 인증에 성공하면, THEN THE System SHALL 세션을 생성하지 않고 접근 거부를 안내하며 해당 시도를 기록한다.
- THE System SHALL 편집자를 개별 사용자로 구분하지 않고, 허용 목록의 모든 편집자에게 동일한 쓰기 권한을 부여한다.
- THE System SHALL 기록의 작성자를 로그인 계정에 귀속시키지 않으며, 시음자 정보를 별도로 입력받거나 저장하지 않는다.
- THE System SHALL 별도의 "편집 모드" 진입 단계를 두지 않고, 쓰기 액션이 시도된 시점에만 인증을 요구한다.
- THE System SHALL 편집·삭제·생성 컨트롤을 세션 유무와 무관하게 동일하게 렌더링한다.
- WHEN 세션이 없는 방문자가 쓰기 액션을 시도하면, THE System SHALL Google 로그인 화면으로 유도하고 인증 완료 후 원래 시도했던 화면으로 복귀시킨다.
- IF 세션이 만료된 상태에서 쓰기 액션을 시도하면, THEN THE System SHALL 입력 중인 내용을 잃지 않도록 보존하고 재로그인 후 해당 액션을 이어서 수행할 수 있게 한다.
- THE System SHALL 편집자 세션을 HttpOnly·Secure·SameSite 속성을 가진 서버 서명 쿠키(JWT)로 유지한다.
- THE System SHALL 편집자 세션에 유효기간을 설정하고, 만료 시 재로그인을 요구한다.
- THE System SHALL 매 요청마다 세션에 담긴 이메일이 허용 목록에 여전히 포함되는지 재검증하고, 제외된 경우 해당 세션을 즉시 무효로 처리한다.
- WHEN 편집자가 로그아웃하면, THE System SHALL 세션 쿠키를 삭제하여 세션을 종료한다.
- THE System SHALL OAuth 흐름에 `state` 값을 쿠키와 대조 검증하여 CSRF를 방어한다.
- THE System SHALL 기록 생성·수정·삭제와 와인 카탈로그 변경을 유효한 편집자 세션이 있는 요청에만 허용한다.
- IF 편집자 세션이 없는 요청이 쓰기 API를 호출하면, THEN THE System SHALL 401을 반환하고 데이터를 변경하지 않는다.
- THE System SHALL 모델 호출·에이전트 실행을 유발하는 모든 엔드포인트를 유효한 편집자 세션이 있는 요청으로만 제한한다.
- THE System SHALL 오디오·이미지를 공개 읽기로 제공하되 원본 스토리지 직접 접근을 차단하고 CDN 경유 요청만 허용한다.
- THE System SHALL 공개 읽기 엔드포인트에 IP 기준 요청 속도 제한을 적용하고, 초과 요청을 차단한다.
- THE System SHALL 인증 경로와 쓰기 API 경로를 검색엔진 크롤링 대상에서 제외한다.

### Requirement 2: 시음 녹음 및 오디오 업로드

**User Story:** As a 시음자, I want 와인을 마시는 순간 바로 녹음하거나 기존 음성 파일을 올리기를, so that 첫 반응을 놓치지 않고 기록할 수 있다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 브라우저에서 마이크 녹음을 시작/일시정지/종료할 수 있는 컨트롤을 제공한다.
- WHILE 녹음이 진행 중이면, THE System SHALL 경과 시간과 실시간 파형(또는 음량 레벨)을 표시한다.
- THE System SHALL 녹음 파일과 업로드 파일 모두 `mp3`, `m4a`, `wav`, `webm` 형식을 허용한다.
- THE System SHALL 단일 오디오 파일 크기를 50MB, 길이를 10분으로 제한한다.
- IF 파일이 형식 또는 크기 제한을 위반하면, THEN THE System SHALL 업로드를 거부하고 위반 사유를 한국어로 표시한다.
- WHEN 오디오 업로드가 완료되면, THE System SHALL 원본을 S3에 저장하고 즉시 분석 작업을 큐에 등록한 뒤 사용자에게 "분석 중" 상태를 반환한다.
- THE System SHALL 녹음에 시음자를 지정하도록 요구하지 않는다.
- THE System SHALL 하나의 시음 세션에 최대 3개의 녹음을 첨부할 수 있게 한다.
- IF 네트워크 중단으로 업로드가 실패하면, THEN THE System SHALL 녹음 데이터를 브라우저에 보존하고 재시도 버튼을 제공한다.

### Requirement 3: 라벨 인식 에이전트

**User Story:** As a 시음자, I want 와인 라벨 사진만 찍으면 와인 정보가 자동으로 채워지기를, so that 마시는 중에 타이핑하지 않아도 된다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 라벨 사진을 카메라 촬영 또는 파일 선택으로 입력받는다.
- WHEN 라벨 사진이 업로드되면, THE **라벨 인식 에이전트** SHALL 와인명, 빈티지, 와이너리, 국가, 지역, 품종, 알코올 도수를 추출한다.
- THE 라벨 인식 에이전트 SHALL 자체 도구를 사용해 기존 와인 카탈로그에서 동일/유사 와인을 먼저 조회하고, 일치하는 항목이 있으면 신규 생성 대신 해당 와인을 후보로 제시한다.
- IF 라벨에서 정보가 불충분하다면, THEN THE 라벨 인식 에이전트 SHALL 외부 웹 검색 도구로 정보를 보강하고 출처를 기록한다.
- THE 라벨 인식 에이전트 SHALL 각 추출 필드에 신뢰도(high/medium/low)를 부여한다.
- WHEN 신뢰도가 low인 필드가 있으면, THE System SHALL 해당 입력 필드를 강조 표시하여 사용자 확인을 유도한다.
- THE System SHALL 자동 추출 결과를 사용자가 저장 전에 모두 수정할 수 있게 한다.
- THE 라벨 인식 에이전트 SHALL 라벨의 비정형 시각 특징(동물/식물/인물/미니멀/화려/필기체/색조 등)을 태그로 추출하여 저장한다. (Requirement 8의 탐색 축 입력)
- THE 라벨 인식 에이전트 SHALL 병 형태·마감(코르크/스크류캡) 등 관찰 가능한 물리 속성을 함께 태깅한다. (Requirement 8의 탐색 축 입력)
- IF 라벨 인식이 실패하면, THEN THE System SHALL 수동 입력 폼으로 전환하고 사진은 그대로 첨부한다.

### Requirement 4: 와인 카탈로그 관리

**User Story:** As a 사용자, I want 와인·와이너리·지역 정보가 구조적으로 관리되기를, so that 같은 와인의 반응 변화와 지역별 취향을 추적할 수 있다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 와인(Wine), 와이너리(Winery), 지역(Region)을 별도 엔티티로 관리한다.
- THE System SHALL 지역을 계층 구조(국가 > 광역 > 세부 산지)로 표현하고 임의 깊이를 허용한다.
- WHEN 사용자가 와인을 등록할 때 동일 와인명·빈티지·와이너리 조합이 이미 존재하면, THE System SHALL 중복 후보를 제시하고 기존 와인에 시음을 추가할지 묻는다.
- THE System SHALL 와인 등록 시 이름을 제외한 모든 필드를 선택 입력으로 허용한다.
- THE System SHALL 와인 검색을 이름·와이너리·지역·품종 부분일치로 지원한다.
- WHEN 와인 정보가 수정되면, THE System SHALL 해당 와인에 연결된 시음 기록을 유지한다.
- IF 시음 기록이 1개 이상 연결된 와인을 삭제하려 하면, THEN THE System SHALL 삭제를 거부하고 연결된 기록 수를 안내한다.
- THE System SHALL 엔티티 간 참조 무결성을 애플리케이션 계층에서 검증하고, 참조가 깨진 데이터가 저장되지 않게 한다.
- THE System SHALL 동시 편집으로 인한 덮어쓰기를 방지하기 위해 쓰기 시 조건부 갱신을 사용한다.

### Requirement 5: 비동기 시음 분석 파이프라인

**User Story:** As a 사용자, I want 녹음을 올린 뒤 기다리지 않고 앱을 계속 쓰다가 분석이 끝나면 알림을 받기를, so that 시음 흐름이 끊기지 않는다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 오디오 분석을 요청-응답이 아닌 큐 기반 비동기 작업으로 처리한다.
- THE System SHALL 분석 파이프라인을 에이전트 그래프로 오케스트레이션하고, 항상 실행되어야 하는 단계는 고정 노드로, 실행 여부가 데이터에 따라 달라지는 단계는 조건부 분기로 표현한다.
- THE System SHALL 판단이 필요하지 않은 단계에 모델 호출을 사용하지 않는다.
- THE System SHALL 각 분석 작업의 상태를 `queued`, `transcribing`, `analyzing`, `completed`, `failed` 중 하나로 노출한다.
- WHEN 오디오가 저장되면, THE System SHALL 트랜스크립션을 수행하여 한국어/영어 혼용 발화를 텍스트로 변환하고 발화별 타임스탬프를 보존한다.
- THE System SHALL 트랜스크립션에 화자 분리를 적용하여 한 녹음에서 최대 2명의 화자를 자동 구분한다.
- WHEN 두 화자가 구분되면, THE System SHALL 화자별 평균 피치를 비교하여 상대적으로 낮은 화자를 `yan`(남성), 높은 화자를 `robert`(여성)로 간주한다.
- THE System SHALL 화자 매핑 결과와 그 신뢰도를 함께 저장하고, 편집자가 두 화자의 매핑을 서로 교체할 수 있게 한다.
- IF 두 화자의 평균 피치 차이가 임계값 미만이어서 성별 판별이 불확실하면, THEN THE System SHALL 실명 매핑을 생략하고 `speaker_1` / `speaker_2`로만 표기한다.
- IF 화자 분리 신뢰도가 낮거나 발화가 심하게 겹쳐 구분이 불가능하면, THEN THE System SHALL 단일 화자로 처리하고 화자 구분에 의존하는 서술을 생성하지 않는다.
- THE System SHALL 오디오에서 음향 특징(RMS 에너지 곡선, 피치 범위, 0.8초 이상 침묵 구간, 발화 속도, 웃음 후보 구간)을 추출하여 분석 에이전트 입력에 포함한다.
- WHILE 분석이 진행 중이면, THE System SHALL 시음 상세 화면에 진행 상태와 예상 소요 시간을 표시한다.
- WHEN 분석이 완료되면, THE System SHALL 화면을 자동 갱신하고 브라우저 알림(허용된 경우)을 발송한다.
- THE System SHALL 트랜스크립션 완료를 폴링이 아닌 이벤트 알림으로 수신하고, 완료를 기다리는 동안 에이전트 실행 세션을 유지하지 않는다.
- THE System SHALL 그래프 실행 상태를 외부 저장소에 지속시키고, 중단된 지점부터 재개할 수 있게 한다.
- THE System SHALL 모든 에이전트 도구를 멱등하게 구현하여, 재실행 시 이미 완료된 단계가 중복 수행되지 않게 한다.
- IF 분석 단계가 일시적 오류로 실패하면, THEN THE System SHALL 지수 백오프로 최대 3회 재시도한다.
- IF 재시도 후에도 실패하면, THEN THE System SHALL 작업을 실패 큐에 격리하고 편집자에게 "재분석" 버튼을 제공하며 원본 오디오와 와인 정보는 보존한다.
- THE System SHALL 트랜스크립트가 비어 있거나 무음인 경우에도 실패로 처리하지 않고, 침묵 자체를 해석 입력으로 사용한다.

### Requirement 6: 소믈리에 분석 에이전트

**User Story:** As a 시음자, I want 짧은 감탄사 한마디도 재미있는 리뷰와 평점, 테이스팅 노트로 확장되기를, so that 전문 지식 없이도 풍성한 기록이 남는다.

**Phase:** 1

#### Acceptance Criteria

- THE **소믈리에 에이전트** SHALL 트랜스크립트, 음향 특징, 와인 메타데이터를 입력으로 받아 다음을 생성한다: 한줄 요약, 반응 하이라이트 목록, 1~5점 평점(0.5 단위), 테이스팅 노트 5축(산미/타닌/바디/향/여운, 각 1~5).
- THE 소믈리에 에이전트 SHALL 도구를 사용해 (a) 같은 와인의 과거 시음 기록, (b) 최근 시음 기록, (c) 품종·지역·5축 스타일이 유사한 과거 시음 기록, (d) 현재 취향 프로파일을 필요할 때 스스로 조회한다.
- THE 소믈리에 에이전트 SHALL 감탄사·의성어를 감정 강도로 매핑하고, 침묵과 웃음도 해석 근거로 사용한다.
- WHEN 발화 내용이 10단어 이하로 짧으면, THE 소믈리에 에이전트 SHALL 서술을 더 과장되고 재미있게 확장한다.
- IF 같은 와인의 과거 시음 기록이 존재하면, THEN THE 소믈리에 에이전트 SHALL 과거 대비 반응 변화 코멘트를 생성한다.
- IF 한 녹음에서 두 화자가 구분되면, THEN THE 소믈리에 에이전트 SHALL 두 화자의 반응을 대비하는 비교 코멘트를 생성하고, 두 화자의 반응 일치도를 0~100으로 산출한다.
- WHEN 화자가 `yan` / `robert`로 매핑되었으면, THE 소믈리에 에이전트 SHALL 비교 코멘트와 하이라이트에 해당 이름을 사용한다.
- IF 화자 매핑이 불확실하면, THEN THE 소믈리에 에이전트 SHALL 이름 대신 중립적 표현으로 두 화자를 지칭한다.
- THE 소믈리에 에이전트 SHALL 각 평점과 노트 축에 대해 근거가 된 발화 또는 음향 신호를 함께 반환한다.
- THE System SHALL AI 평점과 별개로 사용자 수동 평점을 저장할 수 있게 하고, 둘 다 있으면 화면에 함께 표시한다.
- THE System SHALL 생성된 요약·하이라이트를 편집자가 수정할 수 있게 하고, 수정 시 원본 AI 생성물을 함께 보존한다.
- THE System SHALL 분석 결과를 구조화된 스키마로 검증하고, 스키마 위반 시 최대 2회 재생성을 시도한다.
- THE System SHALL 트랜스크립트와 생성된 노트에 대해 부분일치 텍스트 검색을 지원한다.

### Requirement 7: 취향 프로파일 에이전트

**User Story:** As a 부부 사용자, I want 기록이 쌓일수록 우리 취향이 요약되고 다음에 살 와인을 추천받기를, so that 와인샵에서 헤매지 않는다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 부부 공통 취향 프로파일 하나만 유지하고, 개인별 프로파일을 생성하지 않는다.
- WHILE 완료된 시음 기록이 5개 미만이면, THE System SHALL 취향 프로파일을 비활성 상태로 표시하고 남은 필요 횟수를 진행률로 보여준다.
- WHEN 완료된 시음 기록이 5개 이상이 되거나 이후 신규 시음이 5개 추가될 때마다, THE **취향 프로파일 에이전트** SHALL 프로파일을 재계산한다.
- THE 취향 프로파일 에이전트 SHALL 평점 4점 이상 기록의 공통 속성(품종, 국가/지역, 5축 스타일, 가격대)을 선호 패턴으로, 2점 이하 기록의 공통 속성을 비선호 패턴으로 도출한다.
- THE 취향 프로파일 에이전트 SHALL 통계 계산을 자연어 추론이 아닌 실행 가능한 계산 도구로 수행하고, 계산 결과를 근거로 요약문을 생성한다.
- THE 취향 프로파일 에이전트 SHALL 각 패턴에 표본 수와 신뢰 수준을 함께 제시하고, 표본이 3건 미만인 패턴은 "참고" 수준으로 표기한다.
- THE System SHALL 취향 프로파일을 5축 레이더 차트와 키워드 태그로 대시보드에 표시한다.
- THE System SHALL 세션별 반응 일치도를 월 단위로 집계해 추이 차트로 표시한다.
- THE System SHALL 와인 상세 화면에 해당 와인의 취향 적합도 뱃지(딱 맞아 / 도전적 / 비선호 구간)를 표시한다.
- THE System SHALL 취향 프로파일을 근거로 다음에 마셔볼 와인 유형 추천 3건과 와인샵용 한줄 구매 가이드를 생성한다.

### Requirement 8: 뜻밖의 패턴 발견 에이전트

**User Story:** As a 부부 사용자, I want 우리가 찾지도 않았는데 "웃음이 터진 시음은 대체로 4점 이상이었다" 같은 뜻밖의 패턴이 저절로 나타나기를, so that 기록을 쌓는 것만으로 우리만의 발견이 생긴다.

**Phase:** 1

#### Acceptance Criteria

- WHEN 새 시음 분석이 완료되어 누적 기록이 갱신되면, THE **패턴 발견 에이전트** SHALL 누적 데이터를 탐색해 예상치 못한 패턴을 자율적으로 찾는다.
- THE 패턴 발견 에이전트 SHALL 정통 축(품종, 지역, 빈티지, 가격대)과 **비전통 축**(라벨 시각 태그, 병 형태·마감, 시음 시각·요일, 음향 특징, 함께 마신 사람, 직전 시음과의 간격)을 모두 탐색 대상에 포함한다.
- THE 패턴 발견 에이전트 SHALL 상관/차이 계산을 자연어 추론이 아닌 실행 가능한 통계 계산 도구로 수행한다.
- THE System SHALL 사용자가 가설을 직접 등록하거나 이론의 적중률을 관리하는 기능을 제공하지 않는다.
- IF 발견된 패턴의 표본이 4건 미만이면, THEN THE System SHALL 해당 패턴을 사용자에게 제시하지 않는다.
- WHEN 표본 4건 이상이고 대조군 대비 뚜렷한 차이가 확인된 패턴이 발견되면, THE System SHALL 해당 패턴을 **발견 카드**로 생성한다.
- THE System SHALL 발견 카드에 패턴 서술, 재미있는 별칭, 근거가 된 시음 기록 링크, 표본 수, 우연 가능성 표기를 포함한다.
- THE System SHALL 여러 축을 동시에 탐색할 때 발생하는 우연한 상관(다중 비교)을 감안해 각 발견 카드의 신뢰 수준을 `약함` / `보통` / `뚜렷함` 중 하나로 표기한다.
- THE System SHALL 이미 제시한 패턴을 중복 제시하지 않고, 동일 패턴은 표본이 늘어난 경우에만 갱신 알림을 표시한다.
- THE System SHALL 발견 카드를 대시보드에 최신순으로 노출하고, 전체 목록을 별도 화면에서 열람할 수 있게 한다.
- THE System SHALL 각 발견 카드에 대해 편집자가 "숨기기"를 선택할 수 있게 하고, 숨긴 패턴은 이후 재제시하지 않는다.
- WHEN 신규 와인이 등록되면, THE System SHALL 해당 와인 속성에 부합하는 기존 발견 카드를 태그로 표시한다.
- IF 완료된 시음 기록이 10건 미만이면, THEN THE System SHALL 패턴 발견 에이전트를 실행하지 않고 안내 문구만 표시한다.

### Requirement 9: 히스토리 탐색 및 상세 뷰

**User Story:** As a 사용자, I want 와인별·지역별·날짜별·평점순으로 기록을 훑어보기를, so that 지난 시음을 다양한 각도로 되새길 수 있다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 대시보드에 최근 시음, 취향 카드, 최근 반응 일치도, 최신 발견 카드, 진행 중인 분석 상태를 표시한다.
- THE System SHALL 와인별 뷰에서 같은 와인의 시음 기록을 시간순으로 나열하고 평점 추이를 선 차트로 표시한다.
- THE System SHALL 지역 계층을 국가 > 지역 > 세부 산지 순으로 탐색 가능하게 하고 브레드크럼을 제공한다.
- THE System SHALL 와이너리별 뷰와 날짜별 타임라인 뷰를 제공한다.
- THE System SHALL 평점순 랭킹 뷰를 제공하고 AI 평점/수동 평점 기준을 선택할 수 있게 한다.
- THE System SHALL 시음 상세 화면에 라벨 사진, 와인 메타데이터, 오디오 플레이어, 트랜스크립트, 반응 하이라이트, 5축 레이더 차트, 감정 타임라인, 해당 와인의 과거 기록을 표시한다.
- THE System SHALL 트랜스크립트와 반응 하이라이트에 화자 이름(또는 매핑이 불확실한 경우 화자 번호)을 함께 표시한다.
- WHEN 오디오 플레이어를 재생하면, THE System SHALL 현재 재생 위치에 해당하는 트랜스크립트 구간을 강조한다.
- THE System SHALL 모든 화면을 모바일 세로 화면(최소 375px 폭)에서 사용 가능하게 렌더링한다.
- THE System SHALL 다크 모드를 기본으로 하고 와인 테마 색상 팔레트를 적용한다.
- THE System SHALL 편집·삭제 컨트롤을 모든 방문자에게 동일하게 표시하고, 세션이 없는 상태에서 실행되면 Google 로그인 흐름으로 전환한다.

### Requirement 10: 에이전트 운영 가드레일 및 관측성

**User Story:** As a 개발자 겸 운영자, I want 에이전트의 실행 과정과 비용을 추적하고 상한을 걸기를, so that 공개 서비스로 운영하면서도 AWS 요금 사고 없이 디버깅할 수 있다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 모든 에이전트 실행에 대해 트레이스(단계, 도구 호출, 입출력 요약, 지연시간, 토큰 사용량, 비용 추정)를 기록한다.
- THE System SHALL 트레이스를 OpenTelemetry 표준 형식으로 수집하여 중앙 관측 백엔드로 전송한다.
- THE System SHALL 오케스트레이터와 하위 에이전트의 실행을 상하위 관계가 드러나는 계층 구조로 기록한다.
- THE System SHALL 에이전트별로 최대 도구 호출 횟수, 최대 토큰 수, 최대 실행 시간 상한을 설정하고 초과 시 실행을 중단한다.
- THE System SHALL 에이전트 런타임이 제공하는 호출당 상한(추론 반복 횟수, 토큰 예산, 실행 시간, 세션 최대 수명, 유휴 세션 타임아웃)을 모두 명시적으로 지정하고 서비스 기본값에 의존하지 않는다.
- THE System SHALL 유휴 세션 타임아웃을 필요한 최소값으로 설정하여 대기 중 자원 점유를 억제한다.
- WHEN 에이전트 실행이 가드레일로 중단되면, THE System SHALL 부분 결과를 보존하고 중단 사유를 트레이스에 기록한다.
- THE System SHALL 일간/월간 모델 호출 비용을 집계하고, 월 예산의 80%와 100% 도달 시 알림을 발송한다.
- IF 월 예산 상한에 도달하면, THEN THE System SHALL 신규 에이전트 실행을 차단하고 편집자에게 안내 메시지를 표시한다.
- THE System SHALL 일간 에이전트 실행 횟수 상한을 설정하고, 초과 시 신규 실행을 다음 날까지 차단한다.
- THE System SHALL 에이전트 실패율, 평균 지연시간, 스키마 검증 실패율을 운영 지표로 노출한다.
- THE System SHALL 프롬프트와 도구 정의를 버전 관리하고, 각 트레이스에 사용된 버전을 기록한다.
- THE System SHALL 에이전트 도구의 데이터 접근을 읽기 전용으로 제한하고, 파라미터화된 질의만 사용한다.
- THE System SHALL 사용자 입력과 시스템 지시를 구분된 채널로 전달하여 프롬프트 인젝션 영향을 완화한다.
- THE System SHALL 트레이스와 운영 지표를 공개 화면에 노출하지 않는다.
- THE System SHALL 개인 오디오/이미지 원본을 외부 모델 학습에 사용하지 않는 구성으로 모델을 호출한다.

### Requirement 11: AWS 인프라, 배포 및 비용

**User Story:** As a 개발자, I want 인프라가 코드로 정의되고 CI/CD로 배포되며 유휴 시 비용이 거의 들지 않기를, so that 취미 프로젝트로 지속 운영할 수 있다.

**Phase:** 1

#### Acceptance Criteria

- THE System SHALL 모든 워크로드를 조직 관리 계정이 아닌 이 프로젝트 전용 AWS 계정에 배포한다.
- THE System SHALL 전용 계정에 서비스 제어 정책(SCP)을 적용하여 허용된 리전과 서비스 외의 사용을 거부한다.
- THE System SHALL 모든 AWS 리소스를 IaC(AWS CDK)로 정의하고 수동 콘솔 변경 없이 재현 가능하게 한다.
- THE System SHALL `dev`와 `prod` 두 환경을 동일한 IaC로 분리 배포할 수 있게 한다.
- THE System SHALL CI가 장기 액세스 키가 아닌 단기 자격증명(OIDC 연동 역할)으로 전용 계정에 배포한다.
- WHEN 기본 브랜치에 변경이 머지되면, THE System SHALL CI 파이프라인에서 린트·타입체크·테스트·빌드를 수행한 뒤에만 배포한다.
- IF CI의 어느 단계라도 실패하면, THEN THE System SHALL 배포를 중단한다.
- THE System SHALL 저장 데이터의 스키마를 코드로 정의하고, 읽기·쓰기 경계에서 검증한다.
- THE System SHALL 저장 데이터에 스키마 버전을 함께 기록하고, 이전 버전 레코드를 읽을 수 있게 유지한다.
- THE System SHALL 에이전트 실행용 컨테이너 이미지를 런타임이 요구하는 CPU 아키텍처로 빌드하고, 이미지 크기를 런타임 상한 이하로 유지한다.
- THE System SHALL 오디오 처리용 대용량 의존성을 에이전트 컨테이너와 분리된 실행 단위로 배포한다.
- THE System SHALL 서비스 도메인을 상위 도메인에서 서브도메인으로 위임받아 전용 계정 내에서 독립적으로 관리한다.
- THE System SHALL 공개 페이지와 정적 자산을 CDN을 통해 캐시하여 제공한다.
- THE System SHALL 공개 읽기 페이지를 CDN에 캐시하고 쓰기가 발생한 시점에만 해당 캐시를 무효화하여, 방문자 트래픽이 오리진과 데이터 저장소에 도달하지 않게 한다.
- THE System SHALL 상시 과금되는 컴퓨팅·네트워크 리소스(상시 실행 컨테이너, 로드밸런서, NAT 게이트웨이, 프로비저닝된 데이터베이스 인스턴스)를 사용하지 않는다.
- THE System SHALL 애플리케이션 런타임과 에이전트 런타임을 요청·소비 기반으로 과금되는 서비스에 배포한다.
- THE System SHALL 데이터 저장소를 프로비저닝된 용량이 아닌 요청당 과금 방식으로 운영하여, 트래픽이 없는 기간에 컴퓨팅 비용이 발생하지 않게 한다.
- THE System SHALL 데이터 저장소를 기동 대기(cold start) 없이 즉시 응답하는 구성으로 운영한다.
- THE System SHALL 애플리케이션이 데이터 저장소에 사설 네트워크 부착 없이 HTTPS API로 접근한다.
- THE System SHALL 공개 서비스이므로 CDN 캐시 정책과 요청 속도 제한으로 트래픽 급증 시 오리진 비용 증가를 억제한다.
- THE System SHALL 태깅이 가능한 모든 리소스에 `Project: waganda` 태그를 부여한다.
- THE System SHALL 환경 구분을 위해 모든 리소스에 환경 태그(`dev` / `prod`)를 함께 부여한다.
- THE System SHALL 모델 추론 비용이 리소스 태그로 귀속되도록 태그가 부여된 추론 프로파일을 통해 모델을 호출한다.
- THE System SHALL 비용 격리를 계정 경계로 확보하고, 조직 전체 조회 시의 일관성을 위해 `Project: waganda` 태그를 함께 유지한다.
- THE System SHALL 목표 월 운영 비용을 USD 10 이하로 설정하고, 기록 활동이 없는 달은 USD 2 이하가 되게 한다.
- IF 월 운영 비용이 목표치를 초과할 것으로 예상되면, THEN THE System SHALL 비용 알림을 발송한다.
- THE System SHALL 데이터 저장소에 시점 복구(point-in-time recovery)를 활성화하고, S3 원본 파일에 버전 관리를 활성화한다.
- THE System SHALL Google OAuth 클라이언트 시크릿과 세션 서명 키를 포함한 모든 시크릿을 소스코드가 아닌 AWS 관리형 시크릿 스토어에서 주입한다.
- THE System SHALL 애플리케이션 및 Lambda 로그를 중앙 로그 그룹에 수집하고 최소 14일 보관한다.

### Requirement 12: 대화형 소믈리에 에이전트

**User Story:** As a 부부 사용자, I want 앱에 말을 걸어 "지난달 제일 좋았던 와인 뭐였지?", "이 와인 우리 취향일까?" 같은 걸 물어보기를, so that 화면을 뒤지지 않고 바로 답을 얻는다.

**Phase:** 2

#### Acceptance Criteria

- THE System SHALL 자연어 질의를 입력받는 대화 인터페이스를 제공한다.
- THE **대화형 소믈리에 에이전트** SHALL 다음 도구를 스스로 선택·조합해 답변한다: 시음 기록 조회, 와인/와이너리/지역 조회, 시음 노트 텍스트 검색, 취향 프로파일 조회, 발견 카드 조회, 통계 계산, 외부 웹 검색.
- THE System SHALL 누적 시음 기록의 요약 표현이 모델 컨텍스트 한도 내에 들어가는 동안에는 별도 벡터 검색 인프라를 도입하지 않는다.
- THE 대화형 소믈리에 에이전트 SHALL 답변에 근거가 된 시음 기록/와인으로 이동하는 링크를 포함한다.
- IF 데이터로 답할 수 없는 질의라면, THEN THE 대화형 소믈리에 에이전트 SHALL 추측하지 않고 데이터 부족을 명시한다.
- THE 대화형 소믈리에 에이전트 SHALL 동일 대화 내 이전 질문의 문맥을 유지한다.
- THE 대화형 소믈리에 에이전트 SHALL 읽기 전용 도구만 사용하고 쓰기 작업을 수행하지 않는다.
- WHILE 에이전트가 도구를 호출하는 중이면, THE System SHALL 현재 수행 중인 단계를 사용자에게 스트리밍으로 표시한다.
- THE System SHALL 대화 기능을 편집자 세션이 있는 요청으로만 제한한다.
- THE System SHALL 대화 히스토리를 저장하고 다시 열어볼 수 있게 한다.
- THE System SHALL 단일 질의당 도구 호출 횟수와 토큰 사용량 상한을 적용하고, 초과 시 부분 답변과 함께 중단 사유를 안내한다.

### Requirement 13: 월간 매거진 다이제스트

**User Story:** As a 부부 사용자, I want 매달 우리 시음 기록이 잡지처럼 정리된 리포트를 받기를, so that 함께 돌아보며 이야기할 거리가 생긴다.

**Phase:** 2

#### Acceptance Criteria

- WHEN 매월 마지막 날이 되면, THE System SHALL 해당 월 시음 기록을 집계해 매거진 다이제스트를 자동 생성한다.
- THE System SHALL 다이제스트에 이달의 베스트/워스트 와인, 명장면 하이라이트, 신규 방문 산지, 반응 일치도 변화, 새로 발견된 패턴, 다음 달 추천을 포함한다.
- THE System SHALL 다이제스트를 공개 웹 페이지와 공유 가능한 이미지 카드로 제공한다.
- IF 해당 월 시음 기록이 없다면, THEN THE System SHALL 다이제스트를 생성하지 않고 대시보드에 안내만 표시한다.
- THE System SHALL 과거 다이제스트를 월별로 다시 열어볼 수 있게 보관한다.

### Requirement 14: 와인샵 스카우터 에이전트

**User Story:** As a 사용자, I want 와인샵에서 후보 와인들 라벨을 여러 장 찍으면 우리 취향에 가장 맞는 걸 골라주기를, so that 매장에서 즉시 결정할 수 있다.

**Phase:** 2

#### Acceptance Criteria

- THE System SHALL 한 번에 최대 6장의 라벨 사진을 업로드받는다.
- THE System SHALL 스카우터 기능을 편집자 세션이 있는 요청으로만 제한한다.
- WHEN 다중 라벨이 업로드되면, THE **스카우터 에이전트** SHALL 각 라벨을 인식하고, 취향 프로파일·발견 카드·과거 시음 기록을 조회해 후보를 순위화한다.
- THE 스카우터 에이전트 SHALL 각 후보에 대해 추천 순위, 예상 평점, 추천/비추천 이유 한줄, 부합하는 발견 패턴을 반환한다.
- THE 스카우터 에이전트 SHALL 과거에 이미 시음한 와인은 별도로 표기하고 당시 평점을 함께 보여준다.
- THE System SHALL 스카우터 결과를 30초 이내에 반환하며, 초과 시 부분 결과를 먼저 표시한다.
- IF 취향 프로파일이 비활성 상태라면, THEN THE 스카우터 에이전트 SHALL 일반적인 와인 정보 기준으로만 비교하고 그 한계를 명시한다.
