# 순서 독립 기록과 와인 컨텍스트 재폴리싱 시나리오

> 기준일: 2026-08-05
> 범위: 사진과 반응 녹음의 입력 순서를 분리하고, 나중에 확정된 와인 정보를 바탕으로 반응 해석을 안전하게 보강하는 분석 시나리오 제안. 구현 변경은 없다.

## 결론

기록 흐름을 **와인 식별 → 녹음 분석**이라는 단일 절차로 두지 말고, 하나의 시음 세션을 두 종류의 입력이 비동기로 합쳐지는 **캡처(capture) 집합**으로 다룬다.

- 사진과 녹음은 어느 쪽이 먼저 와도 같은 `tastingId`에 붙인다.
- 오디오가 먼저 준비되면 음성·음향만 근거로 한 **반응 초안(reaction draft)** 을 만든다.
- 와인 식별 또는 보강으로 와인 정보가 충분해지면, 원자료를 다시 처리하지 않고 **컨텍스트 폴리싱(contextual polish)** 만 별도 실행한다.
- 폴리싱은 발화·음향에서 확인되지 않는 감상을 사실처럼 만들지 않는다. 와인 정보는 애매한 표현을 해석하거나 서술을 풍성하게 하는 보조 근거이며, 그 사용 사실과 근거를 남긴다.
- 사람이 편집한 요약·하이라이트는 어떤 자동 재분석도 덮어쓰지 않는다.

권장안은 새 `Capture` 엔티티를 추가해 나중에 `Tasting`으로 승격하는 방식이 아니라, **기존 `Tasting`을 캡처 수명주기로 확장**하는 방식이다. 첫 입력 시점에 안정적인 `tastingId`를 만들면 녹음 S3 키, Transcribe 이벤트, 라벨 사진, 재시도 작업이 모두 같은 식별자를 공유한다. 별도 엔티티를 만들면 첨부물 이동과 두 ID의 연결·복구 문제가 추가된다.

## 현재 결합 지점과 한계

현재 `/record`는 라벨 사진을 업로드·인식한 뒤 `Wine`과 `Tasting`을 즉시 만들고, 그 뒤에만 `AudioRecorder`를 활성화한다. `Tasting.wineId`와 `TastingInput.wineId`가 필수이며 `createTasting()`도 와인 참조를 먼저 검증한다. 따라서 녹음부터 시작할 수 없다.

분석도 입력 변화가 아니라 단일 완료 작업으로 모델링돼 있다.

- `TASTING#<id>` 파티션에 `ANALYSIS` 하나와 `JOB` 하나만 있다.
- `Job.completedSteps`는 한 번의 선형 그래프를 재개하는 용도다. 완료 후 와인 메타데이터가 바뀌었는지는 표현하지 못한다.
- AgentCore 세션 B는 `load_state → map_speakers → sommelier_analysis → … → persist_and_publish`로 고정돼 있으며, 소믈리에 노드는 실질적으로 녹음만 프롬프트에 넣는다. 프롬프트에는 와인 정보 입력을 요구하지만 현재 노드가 와인을 적재·스냅샷하지 않는다.
- `persist_and_publish`는 기존 `ANALYSIS`를 덮어쓴다. 편집본은 별도 필드라 보존되지만, AI 초안과 와인 정보가 반영된 AI 결과의 계보는 남지 않는다.
- 취향 프로파일과 발견은 분석 완료 뒤 바로 갱신된다. 초안과 최종 폴리싱이 둘 다 집계되면 중복 집계나 불필요한 모델 호출이 생길 수 있다.

즉, 현재 구조는 “사진이 준비된 단 한 번의 분석”에는 맞지만, “반응 원자료는 먼저 확보하고 맥락은 나중에 합친다”는 흐름에는 맞지 않는다.

## 목표와 비목표

### 목표

1. 사진·녹음·수동 와인명 중 어느 하나를 첫 입력으로 받아 즉시 세션을 시작한다.
2. 트랜스크립트·음향 특징·화자 매핑은 와인 유무와 무관하게 한 번만 만들고 재사용한다.
3. 와인 정보의 생성·수정·보강이 반응 해석에 영향을 주는 경우에만 재폴리싱한다.
4. 분석 결과마다 입력 스냅샷과 생성 이유를 남겨 “무엇이 바뀌어 다시 썼는지”를 추적한다.
5. 공개 화면·취향 프로파일·발견에는 확정 가능한 결과만 반영한다.
6. 라벨 인식·웹 검색·Bedrock 호출을 이벤트마다 무조건 반복하지 않고, 입력 변경 기준으로 멱등하게 합친다.

### 비목표

- 라벨 정보만으로 사용자의 실제 반응·평점·테이스팅 노트를 단정하지 않는다.
- 와인 정보 수정 때마다 Transcribe나 음향 추출을 다시 수행하지 않는다.
- 에이전트가 유료 검색을 자율적으로 여러 번 호출하게 하지 않는다. 기존처럼 빈 필드일 때 코드가 한 번만 제어해 호출한다.
- 사람의 편집 결과를 모델이 자동으로 재작성하지 않는다.

## 권장 데이터 수명주기

### 1. `Tasting`을 비공개 캡처 상태로 먼저 만든다

첫 사진 또는 첫 녹음 등록 시 `Tasting`을 만들되, 와인이 아직 없으면 `wineId`를 비운다. 이 상태는 공개 시음 기록이 아니라 편집자만 보는 작업 중 캡처다.

```ts
type TastingLifecycle =
  | 'collecting' // 사진·녹음 중 하나만 있거나 업로드 중
  | 'awaiting_wine' // 반응 원자료는 준비됐지만 와인 연결 전
  | 'awaiting_audio' // 와인은 연결됐지만 녹음 없음
  | 'reaction_ready' // 음성 기반 반응 초안 생성 완료
  | 'polishing' // 와인 컨텍스트를 합친 재해석 중
  | 'ready' // 공개 가능한 최종 분석 있음
  | 'failed'; // 복구 가능한 특정 작업 실패
```

스키마의 핵심 변경은 다음과 같다.

- `Tasting.wineId` 및 `TastingInput.wineId`를 선택으로 바꾸고 `lifecycle`을 추가한다.
- `createTasting()`은 `wineId`가 있을 때만 참조 무결성을 검사한다.
- `PATCH /api/tastings/[id]/wine` 같은 **결정론적 연결 서비스**가 와인 참조와 라벨 사진을 원자적으로 연결하고 수명주기를 전이한다.
- 타임라인·랭킹·와인별 목록·취향 프로파일은 기본적으로 `lifecycle === 'ready'`만 읽는다. `collecting`~`polishing`은 편집자 세션의 기록 작업함에서만 보인다.
- 기존 완료 시음은 마이그레이션 시 `lifecycle: 'ready'`를 채운다. 와인 참조가 없는 기존 손상 레코드는 공개하지 않고 정정 대상으로 격리한다.

이 선택은 현행 `TASTING#<id>` 파티션과 `REC#<id>`, `ANALYSIS` 키를 그대로 살린다. 단, `TastingSummaryView` 등 현재 `wineId`를 필수로 가정하는 읽기 모델은 공개용 필터를 먼저 적용한 뒤에만 조립하도록 바꿔야 한다.

### 2. 원자료와 해석 결과를 분리한다

`Recording`에 이미 보존되는 오디오 키·트랜스크립트·음향 특징·화자 매핑은 **불변에 가까운 원자료**다. 이들은 한 번 확보하면 재폴리싱에서 다시 만들지 않는다.

분석 결과는 현재의 단일 최신 `Analysis` 외에, 같은 시음 파티션에 실행별 스냅샷을 남기는 `AnalysisRevision`을 둔다.

```ts
type AnalysisStage = 'reaction_draft' | 'contextual_polish';

interface AnalysisRevision {
  tastingId: string;
  revisionId: string;
  stage: AnalysisStage;
  reason: 'audio_ready' | 'wine_attached' | 'wine_metadata_changed' | 'manual_reanalyze';
  inputFingerprint: string;
  recordingRevisions: Record<string, number>;
  wineSnapshot?: { wineId: string; rev: number; fields: string[] };
  result: SommelierOutput;
  promptVersion: string;
  modelId: string;
  createdAt: string;
}
```

- `ANALYSIS#<revisionId>`처럼 별도 정렬 키를 두고, 기존 `ANALYSIS`는 현재 자동 결과의 공개용 포인터/투영으로 유지한다.
- `inputFingerprint`은 녹음 ID·녹음 `rev`·와인 ID·와인 `rev`·프롬프트 버전·분석 단계의 해시다. 같은 입력에 같은 단계가 이미 성공했으면 실행하지 않는다.
- `Analysis.editedSummary`와 `editedHighlights`는 기존 정책대로 별도 유지한다. 새 자동 결과가 생겨도 편집본이 있으면 화면에는 편집본을 우선 표시하고, “새 분석 제안 있음”으로 비교·적용을 명시적으로 선택하게 한다.
- 화면에는 최신 결과만 기본 표시하되, 편집자는 “반응 초안”과 “와인 정보 반영본”의 변경 이유·생성 시각·근거를 확인할 수 있어야 한다.

## 에이전트·그래프 시나리오

에이전트가 다음 행동을 자율 판단하는 구조가 아니라, 입력 이벤트를 받아 **결정론적 조정기(reconciler)** 가 필요한 작업만 큐에 넣는 구조가 적합하다. 모델 호출은 `reaction_draft`와 `contextual_polish` 두 해석 노드에만 한정한다.

```text
사진 업로드 ─→ 라벨 인식/보강 ─→ 와인 후보 확정·연결 ─┐
                                                      ├→ reconcile_capture
녹음 업로드 ─→ 전사·음향·화자 매핑 ─→ 반응 초안 생성 ────┘

reconcile_capture:
  원자료 준비 + 와인 미연결    → awaiting_wine 유지
  원자료 준비 + 와인 연결      → contextual_polish enqueue
  와인 연결 + 원자료 없음      → awaiting_audio 유지
  폴리싱 성공                  → ready 게시 → 프로파일/발견 갱신
```

### A. 녹음 먼저

1. 사용자가 녹음을 시작하면 즉시 `Tasting(lifecycle: 'collecting')`을 만든다. 와인명 입력을 요구하지 않는다.
2. 녹음 업로드 후 세션 A가 Transcribe·음향 추출을 수행한다. 각 녹음 단위 작업은 독립적으로 멱등 처리한다.
3. 원자료가 준비되면 `reaction_draft`가 트랜스크립트·음향·화자 정보만으로 요약·하이라이트·반응 강도를 만든다. 와인 스타일을 전제로 한 5축 노트나 품종 관련 단정은 생략 가능하다.
4. 세션은 `awaiting_wine` 또는 `reaction_ready`로 남는다. 사용자는 사진을 지금 찍거나 나중에 붙일 수 있다.
5. 사진 인식이 기존/신규 와인을 연결하면 조정기가 `contextual_polish`를 한 번 예약한다.
6. 폴리싱 성공 후에만 `ready`로 전이하고 공개·프로파일·발견 갱신을 수행한다.

### B. 사진 먼저

1. 사진 업로드 시 `Tasting(lifecycle: 'collecting')`을 만들고 라벨 인식·보강 결과로 와인을 연결한다.
2. 세션은 `awaiting_audio`가 되고, 현재처럼 녹음 버튼을 기다린다.
3. 녹음 원자료가 준비되면 반응 초안을 건너뛰거나(지연을 우선할 때) 생성한 뒤 즉시 폴리싱까지 이어서 실행한다.
4. 최종 결과만 `ready`로 게시한다. 사진 먼저 경로가 현재 UX보다 단계가 하나 늘어나지 않도록, 조정기는 두 모델 호출을 하나의 백그라운드 작업군으로 다룬다.

### C. 거의 동시에 입력하거나 와인 정보가 나중에 보강됨

- 사진과 녹음 이벤트는 도착 순서를 신뢰하지 않는다. 둘 모두 처리 후 `reconcile_capture(tastingId)`를 호출한다.
- 라벨 인식 후 웹 검색 보강으로 품종·산지 등이 추가되면 `wine.rev` 또는 분석 관련 필드의 스냅샷이 바뀐다. 조정기가 기존 `contextual_polish`의 fingerprint와 비교해 정말 달라졌을 때만 새 폴리싱을 예약한다.
- 같은 와인에 연결된 다른 시음까지 자동 재분석하지 않는다. 와인 정보가 변경된 각 기록에는 “재폴리싱 가능” 표시만 하고 편집자가 일괄/개별 실행을 선택한다. 과거 공개 기록이 조용히 바뀌는 것과 비용 폭증을 막는다.

## 폴리싱 프롬프트와 근거 규칙

`contextual_polish`는 원 트랜스크립트만 다시 읽는 대신 다음을 함께 입력한다.

- `reaction_draft` 결과와 그 인용·음향 근거
- 불변 원자료: 트랜스크립트, 음향 특징, 화자 매핑
- 와인 메타데이터 스냅샷: 이름, 빈티지, 품종, 지역, 알코올 도수, 라벨/검색 출처
- 필요할 때만 같은 와인·유사 와인의 과거 기록과 취향 프로파일

모델에는 아래 경계를 명시한다.

1. 발화·음향은 **반응의 1차 근거**다. 없는 향·맛·평점을 와인 일반 지식만으로 만들지 않는다.
2. 와인 정보는 애매한 표현의 후보를 좁히거나, 문장 맥락을 보강하는 **2차 컨텍스트**다. 예를 들어 “묵직하다”는 말에 품종·도수 정보를 곁들일 수 있지만, 사용자가 말하지 않은 블랙베리·오크 향을 실제 경험처럼 서술하지 않는다.
3. 와인 컨텍스트를 사용한 필드는 `Evidence.kind: 'wine_context'`와 스냅샷 출처를 남긴다. 현재 `quote | acoustic | history` 열거형을 확장해야 한다.
4. AI 평점·5축 노트는 반응 근거가 충분할 때만 생성한다. 컨텍스트만으로 채운 항목은 “와인 정보 참고” 성격을 별도 표시하고, 수동 평점이나 실제 발화 기반 판단과 혼동하지 않는다.
5. 결과는 시음 일기 문체를 유지한다. 내부 근거의 기술적 라벨은 공개 서술에 노출하지 않는다.

이 규칙이 없으면 “이 와인은 보통 타닌이 강하다”가 “이번에 타닌이 강했다고 느꼈다”로 바뀌는 환각이 생긴다. 사용자가 전문 표현을 충분히 하지 않았다는 문제는 해결하되, 기록의 진실성은 지킨다.

## 작업 모델과 멱등성

현행 `JOB` 하나를 초기화해 재사용하면 사진·녹음·재폴리싱이 겹칠 때 서로의 `completedSteps`와 상태를 지운다. 작업을 실행 단위로 분리한다.

```ts
type AnalysisJobKind = 'prepare_recording' | 'reaction_draft' | 'contextual_polish' | 'publish';

interface AnalysisJob {
  tastingId: string;
  jobId: string;
  kind: AnalysisJobKind;
  inputFingerprint: string;
  status: 'queued' | 'running' | 'completed' | 'failed' | 'superseded';
  attempts: number;
  resultRevisionId?: string;
}
```

- 저장 키는 `JOB#<jobId>`로 바꾸고, 필요하면 `JOB#CURRENT`에 화면용 집계 상태만 둔다. 현재 `JOB` 단일 정렬 키와 단일 `recordingId` 가정은 여러 녹음·후속 폴리싱에 맞지 않는다.
- `prepare_recording`은 recording ID를 포함한 fingerprint로 멱등화한다. 새 녹음이 추가됐다고 기존 녹음의 전사·음향 추출을 반복하지 않는다.
- `reaction_draft`와 `contextual_polish`는 사용한 모든 녹음의 ID/rev를 fingerprint에 넣는다. 녹음을 추가하면 새 초안/폴리싱이 필요하지만, 와인만 수정하면 전사 단계는 건너뛴다.
- 동일 fingerprint의 `queued`/`running` 작업이 있으면 새 작업을 만들지 않는다. 아직 시작하지 않은 이전 fingerprint 작업은 `superseded` 처리한다.
- 실패는 해당 작업에 귀속하고 재시도 버튼도 “전사 다시 시도”, “반응 초안 다시 생성”, “와인 정보 반영 다시 생성”으로 분리한다.

AgentCore Runtime의 세션은 완료 대기용 상태 저장소가 아니다. Transcribe 완료는 기존처럼 EventBridge가 깨우고, 각 이벤트는 `tastingId`와 `recordingId`/`jobId`로 조정기를 호출한다. `completedSteps`는 단일 전체 그래프가 아니라 각 작업의 세부 재개에만 사용한다.

## API와 화면 제안

### API 경계

HTTP 라우트는 인증·파싱·상태 코드만 담당하고, 수명주기 판정은 `lib/services/captures.ts` 같은 서비스 계층으로 둔다.

- `POST /api/captures` — 첫 입력 직전에 빈 캡처 시음 생성. 응답은 `tastingId`.
- `POST /api/tastings/[id]/recordings` — 와인 연결 여부와 무관하게 녹음 사전 서명/레코드 생성.
- `POST /api/tastings/[id]/label` — 사진 업로드 키를 연결하고 라벨 인식 결과를 처리한 뒤 와인 후보를 연결.
- `POST /api/tastings/[id]/wine` — 기존 와인 선택 또는 수동 이름으로 연결.
- `POST /api/tastings/[id]/reconcile` — 내부 이벤트용. 현재 입력 상태를 보고 필요한 작업만 예약. 브라우저는 직접 파이프라인 종류를 결정하지 않는다.
- `POST /api/tastings/[id]/analyses/repolish` — 편집자가 명시적으로 최신 와인 정보 반영을 요청. 비용 발생 엔드포인트이므로 기존과 같이 편집자 가드가 필수다.

기존 `/api/tastings/[id]/analyze`는 “전체 재분석” 의미를 없애고, 임시 호환 후 위 작업별 엔드포인트로 분리한다. 외부 호출은 모두 주입 가능한 클라이언트/인보커를 유지해 테스트가 실제 Bedrock·Transcribe를 호출하지 않게 한다.

### `/record` UX

첫 화면은 순서 번호 대신 같은 비중의 두 카드로 시작한다.

```text
[ 라벨 사진 찍기 / 고르기 ]     [ 지금 반응 녹음하기 ]
          ↓                               ↓
    와인 알아보는 중                  반응 정리하는 중
          └──────── 같은 기록에 자동으로 모임 ────────┘

와인이 확인되면: “와인 정보를 반영해 반응을 다듬고 있어요.”
완료되면:         “기록 완성 — 와인 정보 참고로 표현을 보강했어요.”
```

- 어느 버튼을 눌러도 즉시 `tastingId`를 만들고 다른 카드가 활성화된다.
- 사진 인식 실패는 현재처럼 사진을 보존하고 수동 이름/기존 와인 선택으로 이어진다. 이 실패가 녹음 시작을 막지 않는다.
- 녹음이 먼저 끝났다면 상세/작업함에서 “와인 사진을 나중에 붙여도 됩니다”와 반응 초안 상태를 보여 준다.
- 와인이 연결된 뒤 자동 폴리싱이 시작된다는 사실, 그리고 폴리싱이 음성 원본을 다시 전사하지 않는다는 사실을 짧게 알린다.
- 최종 공개 전에는 불완전 캡처를 타임라인에 노출하지 않는다. 편집자에게만 이어서 기록/삭제/재시도 행동을 제공한다.

## 집계·게시 규칙

- `reaction_draft`는 개인 작업 중 결과다. 타임라인, RSS, 와인 평균 평점, 취향 프로파일, 발견 카드, CloudFront 공개 캐시 무효화의 원인이 되지 않는다.
- `contextual_polish`가 성공해 `ready`가 될 때만 기존 `persist_and_publish`에 해당하는 공개 투영·캐시 무효화·프로파일/발견 갱신을 실행한다.
- **RSS 항목은 다음 조건을 모두 만족할 때만 포함한다.** (1) 라벨 사진이 연결되고 와인 식별/수동 확인으로 `wineId`가 확정됨, (2) 녹음이 하나 이상 있고 전사·음향 원자료가 준비됨, (3) 그 입력 스냅샷을 사용한 최신 `contextual_polish`가 성공해 `lifecycle === 'ready'`임. 사진만 있거나 음성 반응 초안만 있는 캡처, 라벨 보강·폴리싱 중인 기록은 RSS에 절대 포함하지 않는다.
- 이 조건은 RSS route의 `getTimelineView()` 조회에도 명시적으로 적용한다. `ready` 상태만으로 암묵적으로 믿지 말고, 와인 연결·라벨 사진·최종 분석 revision의 입력 fingerprint까지 검증한다. RSS는 pull 피드이므로 조건 충족 전에는 캐시 무효화로 새 항목을 보이지 않게 하고, 조건을 충족해 처음 게시되는 시점에만 기존 `/*` 무효화로 피드를 갱신한다.
- 이미 `ready`인 시음을 수동 재폴리싱할 때는 최종 `Analysis` 투영만 조건부 갱신한다. 프로파일/발견은 분석의 입력값(평점·노트)이 실제로 변경됐을 때만 한 번 갱신한다.
- 수동 평점은 항상 AI 결과보다 표시 우선이고, 재폴리싱으로 수정하지 않는다.

## 구현 순서와 계약 테스트

### 1단계 — 데이터·조회 안전망

1. `Tasting`에 optional `wineId`와 `lifecycle`을 추가하고 기존 레코드 업캐스트를 작성한다.
2. 공개 읽기 모델이 `ready`가 아닌 캡처를 절대 노출하지 않는지 고정한다.
3. 미연결 시음은 편집자 작업함에서만 와인명 “확인 중”으로 표현한다.
4. `AnalysisRevision`과 실행별 Job 저장 계약, optimistic locking, 입력 fingerprint 비교를 단위 테스트한다.

### 2단계 — 입력 순서 독립 UX

1. `/record`에서 최초 사진·녹음 어느 쪽도 캡처를 만들 수 있게 바꾼다.
2. 라벨 연결·수동 와인 선택·기존 와인 중복 연결을 캡처 상태 전이로 통합한다.
3. 녹음 업로드가 `wineId` 부재 때문에 거절되지 않는지, 라벨 인식 실패 뒤에도 녹음 가능한지 E2E로 고정한다.

### 3단계 — 분리된 분석 그래프

1. `prepare_recording`을 기존 세션 A의 Transcribe·음향 추출·화자 매핑으로 분리한다.
2. `reaction_draft`와 `contextual_polish`를 별도 노드/프롬프트/출력 revision으로 만든다.
3. 조정기가 이벤트 순서와 중복 전달에 대해 같은 작업을 한 번만 예약하는지 테스트한다.
4. `wine_context` 근거가 없는 모델 출력은 검증에서 거부하고, 컨텍스트만으로 실제 감상을 단정하는 금지 사례를 프롬프트 회귀 테스트로 둔다.

### 4단계 — 게시·운영

1. 폴리싱 성공 시에만 `ready` 게시·캐시 무효화·프로파일/발견 갱신을 연결한다.
2. 작업별 실패·재시도·superseded 상태를 상세 화면과 CloudWatch 로그에서 구분한다.
3. 실제 AWS 호출 검증은 소수의 샘플로 제한한다. 로컬 DB/S3는 에뮬레이터지만 Bedrock·Transcribe는 실제 과금이므로 테스트 루프에 넣지 않는다.

핵심 계약 테스트는 다음을 포함한다.

- 녹음 먼저: 와인 없이 캡처·녹음·반응 초안이 저장되고 공개 목록에는 나타나지 않는다.
- 사진 나중: 와인 연결 뒤 원자료 재처리 없이 `contextual_polish` 하나만 추가된다.
- 사진 먼저: 기존과 동등하게 최종 결과까지 진행하며 불필요한 중간 공개가 없다.
- 동시 이벤트·중복 EventBridge 이벤트: 같은 fingerprint의 모델 호출은 한 번이다.
- 와인 메타데이터 변경: 관련 필드가 바뀌었을 때만 폴리싱이 예약되고, Transcribe·음향 작업은 재실행되지 않는다.
- 편집본 보존: 새 AI revision이 생겨도 `editedSummary`/`editedHighlights`가 덮어써지지 않는다.
- 근거 안전성: 컨텍스트를 사용한 항목에는 `wine_context` 출처가 남고, 발화·음향 근거 없는 감각 단정은 거부된다.
- 시간대: 캡처 시각과 시음 시각의 요일·시간대 파생은 항상 `SERVICE_TIME_ZONE`(`Asia/Seoul`)을 사용한다.

## 결정이 필요한 항목

1. **초안 공개 시점:** 권장안은 와인 연결과 폴리싱 후에만 `ready`로 공개한다. 와인 미확정 반응 초안을 비공개 작업함에서만 보이는 것으로 확정할지 결정이 필요하다.
2. **자동 폴리싱 범위:** 권장안은 현재 작업 중인 시음은 자동, 이미 공개된 과거 시음은 수동이다. 과거 전체를 자동 갱신하면 비용·기록 변경 추적 문제가 커진다.
3. **컨텍스트 표시:** 권장안은 최종 화면에 “와인 정보 참고”를 가볍게 표시하고, 상세 근거는 편집자만 볼 수 있게 한다. 독자에게도 상세 근거를 공개할지는 별도 제품 결정이다.
