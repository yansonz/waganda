# AgentCore 활용 검토 — 관리형 에이전트·메모리를 얹을 가치가 있는가

> 기준일: 2026-07-30
> 범위: 현재 구현된 코드베이스를 근거로 한 설계 판단. 구현 변경은 없다.

## 요약

| 대상 | 판단 | 이유 |
| --- | --- | --- |
| 관리형 에이전트 오케스트레이션(Bedrock Agents) — 분석 파이프라인에 적용 | **도입하지 않음** | 단계가 고정된 워크플로다. 모델이 순서를 고를 여지가 없다 |
| AgentCore 장기 메모리 — 취향 프로파일 대체 | **도입하지 않음** | 이미 DB 기록에서 결정론적으로 계산한다. 근거 추적·재현성·비용 모두 현재 방식이 낫다 |
| AgentCore 단기 세션 — 대화형 기능 | **필요해지면 도입** | 다중 턴 지시어 해석에 실제로 필요하다. `agent/src/lib/session.ts` 에 이미 구성돼 있다 |
| AgentCore 장기 메모리 — 대화에서만 드러나는 선호 | **조건부 도입** | 기록으로 환원되지 않는 정보에 한정. 프로파일과 분리 표시 필수 |
| AgentCore Browser — 라벨 보강 심화 | **검토 가치 있음** | 현재 보강 품질 문제를 직접 해결한다 |

## 1. 파이프라인에 오케스트레이션이 필요 없는 이유

관리형 에이전트가 값을 주는 조건은 **모델이 다음 행동을 스스로 골라야 할 때**다. 도구가 여럿인데 어느 것을 몇 번 쓸지 미리 알 수 없는 상황에서 ReAct 루프·액션 그룹·트레이스가 유용하다.

`agent/src/graph/nodes/` 의 실제 단계는 고정돼 있다.

```
loadState → ensureJob → startTranscription → extractAcoustic
          → mapSpeakers → sommelierAnalysis → persistAndPublish
          → refreshProfile → runDiscovery
```

모델이 판단할 여지가 있는 지점은 실질적으로 `sommelierAnalysis` 하나이고, 그 출력은 zod 스키마(`packages/schemas/src/analysis.ts`)로 고정돼 있다. 여기에 오케스트레이션 루프를 넣으면

- 모델이 순서를 틀릴 자유가 생긴다
- 판단 토큰이 추가로 든다
- 실패 지점이 늘고, **어느 노드에서 깨졌는지 Job 레코드로 즉시 알 수 있는 현재의 명확함을 잃는다**

## 2. 장기 메모리로 취향 프로파일을 대체하지 않는 이유

AgentCore 장기 메모리의 대표 용도가 `UserPreferenceMemoryStrategy` 를 통한 "사용자 취향 자동 축적"이다. 이름만 보면 와간다의 취향 프로파일과 겹친다. 그러나 이 프로젝트는 `lib/domain/profile.ts` 의 `buildTasteProfile()` 로 DynamoDB 기록에서 순수 함수로 계산한다.

| | 결정론적 집계 (현재) | 장기 메모리 |
| --- | --- | --- |
| 근거 | 어느 시음이 어느 축에 기여했는지 추적 가능 | 추출 결과만 남고 근거가 흐려진다 |
| 재현성 | 같은 입력 → 같은 출력. 단위 테스트 가능 | 추출 모델에 따라 흔들린다 |
| 비용 | 없음 | 추출·저장·검색 과금 |
| 수정 | 기록을 고치면 즉시 반영 | 잘못 기억한 것을 지우기 어렵다 |

기록 규모가 두 사람 × 수십 건이면 전체를 읽어 계산하는 것이 정확하고 무료다. 의미 검색이 필요한 시점은 원문이 수천 건이라 전부 읽을 수 없을 때다.

## 3. 기능 제안 (우선순위 순)

### 3.1 매장 결정 도우미 `/pick` — 가장 값이 크다

**해결하는 공백:** 기록은 쌓이는데 정작 와인을 살 때 그 기록을 쓰지 못한다. 진열대 앞에서 타임라인을 뒤지는 것은 현실적으로 안 된다.

```
[진열대 사진 3~4장 촬영]
  ↓
Château Bellevue 2019          [잘 맞음]
  타닌 강한 보르도 — 두 사람 평균 4.3점대 취향
  ⚠ 2025.11 마셨습니다 (4.5점, "긴 여운")

Sauvignon Blanc 2023           [안 맞음]
  로버트가 낮게 준 계열 (n=2, 평균 2.8)

Barolo 2018                    [잘 맞음] ← 추천
  기록 없음 · 묵직한 레드 선호와 일치
```

> "둘 다 이미 마셔봤어" → 다음 후보로 대화 진행

**재사용:** `assessFit()`(FitLevel 계산), `FitBadge` 컴포넌트, 읽기 도구 `findWines`·`getTasteProfile`·`getTastingsForWine`·`findSimilarTastings`, 라벨 인식 경로(`lib/agent/labelDirect.ts`).
**새로 필요:** 다중 후보 비교, 대화 턴.

다중 턴이 실제로 필요한 첫 기능이다 — "이미 마셔봤어", "너무 비싸", "둘 중 어느 쪽" 같은 지시어를 해석할 세션 맥락이 있어야 대화가 성립한다.

### 3.2 우리 기록에 물어보기 (대화형 열람)

타임라인 상단 자연어 질의창. "작년 여름에 마신 화이트 중 로버트가 좋아했던 것", "요즘 내 취향이 바뀌었나".

읽기 전용 도구만 쓰므로 비로그인 열람 정책과 그대로 맞는다.

**필수 제약:** 모든 답변에 **근거 시음 링크**를 붙인다. 발견(discovery) 화면의 "근거 시음" 패턴을 재사용한다. 근거 없는 요약만 내놓으면 환각을 검증할 방법이 없다.

### 3.3 AgentCore Browser 로 라벨 보강 심화

현재 보강(`lib/agent/labelEnrich.ts`)은 SerpAPI **검색 스니펫만** 본다. 그래서 `confidence: low` 가 많고 출처도 3건에서 그친다. 실측 예: 산지가 `Australia` 까지만 채워졌다.

Browser 로 wine-searcher·Vivino 페이지를 실제로 열면 빈티지별 평균가·평점·상세 산지를 읽을 수 있다. 비용은 브라우저 세션 과금과 수십 초 지연이므로, 초안 생성 직후 백그라운드로 돌리고 완료 시 카드를 갱신하는 형태가 맞다.

### 3.4 장기 메모리 = 대화에서만 드러나는 선호

시음 기록으로 환원되지 않는 발화가 있다.

> "요즘 단 건 물린다", "로버트는 오크 강한 걸 못 마신다"

이 정보는 `UserPreferenceMemoryStrategy` 가 자동 추출할 수 있다. 단 두 가지를 지켜야 한다.

- **프로파일과 분리 표시** — "기록에서 계산한 것"과 "대화에서 알게 된 것"을 섞으면 근거를 잃는다
- **출처와 삭제 수단** — 각 항목에 어느 대화에서 왔는지 표시하고 삭제 버튼을 둔다. 잘못 기억한 것을 지울 수 없는 것이 장기 메모리의 가장 큰 위험이다

### 3.5 Gateway 로 읽기 도구를 MCP 로 노출

`agent/src/tools/` 의 9개 도구(`computeStats`, `findSimilarTastings`, `findWines`, `getRecentTastings`, `getTasteProfile`, `getTastingsForWine`, `getWine`, `listDiscoveries`, `webSearch`)를 MCP 서버로 내보내면 웹앱·파이프라인·외부 클라이언트가 같은 도구를 공유한다.

각자 쓰는 MCP 클라이언트에서 바로 기록에 질의할 수 있으므로, **새 화면을 만들지 않고 3.2 의 가치를 얻는 우회로**가 된다. 접근 제어는 AgentCore Identity 를 `EDITOR_ALLOWLIST` 와 묶는다.

### 3.6 나중에 볼 것

- **Code Interpreter** — 기록 30건 이상일 때. 결정론적 집계는 미리 정한 5축만 계산하므로, "가격과 평점이 상관있나" 같은 예상 못 한 축은 코드로 찾는 편이 맞다. 보완 관계다
- **Runtime 장기 실행** — 정기 태그 인사이트 배치. 현재 규모에서는 단발 호출로 충분하다

## 4. 진행 시 주의

**AgentCore Runtime 배포는 아직 한 번도 검증되지 않았다** (`spike-findings.md` 의 2.2·2.3·2.5 미확인). 스파이크에서 `GraphBuilder`·`S3SessionManager` 가 SDK 에 없어 설계를 바꿔야 했던 것처럼, 런타임 배포에서도 전제 이탈이 나올 수 있다.

따라서 3.1 을 만들 때는 **로컬 직접 호출로 프로토타입해 UX 유용성을 먼저 확인하고**, 그다음 Runtime 에 올리는 순서를 택한다. `lib/agent/labelDirect.ts`·`sommelierDirect.ts` 가 이미 그 패턴이다.

또한 정기 태그 인사이트 탐색(기록 10건 이후 판단하기로 한 항목)에는 메모리가 필요 없다. 배치로 전체를 읽어 한 번 호출하는 것이 단순하고 결과 검토가 쉽다.
